The formula

session_MiB = 8.04 × (D/90) × (H/19) × F ← eBPF half + 4.23 × (D/90) ← EventPipe half, fixed 1 kHz ingest_GiB_day = pods × sessions × session_MiB / 1024 ingest_$ = ingest_GiB_day × 30.4 × P_ingest retain_$ = ingest_GiB_day × 1.5 × R × P_retain × 30.4 ← 1.5 = index expansion query_$ = views × scan_GiB × P_query × 30.4 compute_$ = (nodes × collector_frac + pods × sidecar_frac) × node_$ where D = seconds, H = eBPF Hz, R = retention days F = 1 if scoped to target services, else 10 scan_GiB = one session (bounded) or R days of data (unbounded) collector_frac = max(0.10 vCPU / node_vCPU, 0.25 GiB / node_GiB) sidecar_frac = max(0.10 vCPU / node_vCPU, 0.25 GiB / node_GiB)
Where this model is soft. Record counts are unique (stack, thread) groups, and unique stacks saturate — a session twice as long does not produce twice as many. Scaling linearly with duration therefore over-estimates long sessions. Treat the number as an upper bound, and re-measure with the DQL in docs/queries/ once you have real traffic.
Excluded on purpose: your existing cluster, CI minutes, and any Dynatrace licensing beyond data. Also excluded — and worth budgeting separately — the EventPipe buffer, which is charged against the profiled application's memory limit rather than the sidecar's, so profiling can OOMKill the workload it observes.
